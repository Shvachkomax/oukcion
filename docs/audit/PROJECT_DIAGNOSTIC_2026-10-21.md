## 1. Краткое резюме

**Что это сейчас.** «Оукцион» — Next.js-витрина на Next.js 16 / React 19 / Supabase, развёрнутая на Vercel. По факту это **одностраничный лендинг** с двумя рабочими маршрутами: `/` (главная, статическая витрина) и `/cabinet/artists` (кабинет оператора по общему секретному коду). Реально работающий и проверенный функционал — **ровно один**: кабинет, в котором оператор заводит карточки публичных персон (`artists`) и привязанные к ним физические товары (`physical_products`), с загрузкой фотографий в Supabase Storage, и публикация опубликованных товаров в блок «Опубликованные позиции» на главной.

**Что можно показать пользователям сейчас.** Аккуратно сверстанный, адаптивный (десктоп + мобильный, без горизонтального скролла), с проходящим WCAG AA контрастом текста лендинг, описывающий три направления площадки, и закрытый кабинет, в котором заводится витрина артистов. Главная при этом **пуста по содержанию**: блок артистов и блок товаров не отрисовываются, потому что на продакшене нет строк в БД (или БД недоступна — см. §2.4), а все товары, услуги и аукционные лоты на главной — **захардкоженные массивы**, не связанные ни с какой таблицей.

**Что не сделано.** Не существует ни каталога, ни поиска, ни фильтров, ни страницы публичной персоны, ни карточки товара, ни корзины, ни заказа, ни оплаты, ни избранного, ни уведомлений, ни аукционной механики, ни модерации как процесса. Услуги как отдельный тип объекта не поддерживаются вообще.

**Главный риск проекта — не в коде, а в управлении.** Локальный репозиторий, с которым работает владелец (`Shvachkomax/Ouction`, приватный), **на 10 дней отстаёт от продакшена** и не содержит вообще ничего из работающей функциональности (кабинет, доступ к БД, SQL-схему). При этом актуальный исходник лежит в **публичном** репозитории `Shvachkomax/oukcion`.

## 3. Готовность дизайна и интерфейса

**Ограничение:** изображения скриншотов приложены, но **модель не поддерживает просмотр изображений** — выводы сделаны по DOM, вычисленным стилям, замерам геометрии и попиксельным замерам текста, а не по визуальному просмотру. Утверждённых макетов в репозиториях не найдено, поэтому дизайн **не считается утверждённым**.

### 3.1 Дизайн-система: продакшен ≠ локальный репозиторий

| | Продакшен (`oukcion`) | Локальный репозиторий (`Ouction`) |
|---|---|---|
| Тема | светлая, `--color-paper #f4f4f5` | тёмная, `--black #070604` |
| Акцент | `--color-ember #ff5a00` | `--gold #d3a44f` |
| Шрифт | `"DM Sans", Inter, …` | `Inter, …` + `Georgia` для заголовков |
| Радиусы | `36px` карточки, `14px` кнопки | иные значения |
| CSS | 16 945 Б | 13 458 Б |

Это **две разные дизайн-системы**. Любая доработка локальной копии не попадёт в прод без переноса.

### 3.2 Шрифты не загружаются

`@font-face` — 0 вхождений; `next/font` — не используется; ссылок на Google Fonts — 0. Замер ширины строки: `"DM Sans"` = `Inter` = `monospace` = **122.05px**, `sans-serif` = **137.13px** ⇒ оба объявленных шрифта **не загружены**, рендерится системный fallback. Заголовки в локальной версии объявляют `Georgia` — системный, но не загруженный явно.

## 4. Карточки товаров

### 4.1 Фактический путь

```
кабинет → создание ✅ → редактирование ✅ → публикация (status=published) ✅
      → главная (блок «Опубликованные позиции») ✅
      → карточка товара ❌ → корзина ❌ → заказ ❌ → оплата ❌
```

Требование «создание → редактирование → публикация → каталог → карточка → корзина → заказ» выполняется **только на первых трёх шагах**. Каталога как отдельной страницы нет: опубликованные товары показываются только в блоке внутри лендинга, ограниченном `limit 12`, и **только если есть хотя бы один featured-артист** (блок вложен в `artists.length > 0 ? … : null`).

## 14. Краткий ответ

### Можно ли сейчас провести демонстрацию?
**Да, но только как демонстрацию витрины, а не платформы.** Показывать имеет смысл: качественную адаптивную главную (десктоп + мобильный, WCAG AA, без горизонтального скролла) и закрытый кабинет оператора (создание артиста, создание товара, загрузка фото, публикация — всё это реально работает и проверено). Перед демонстрацией обязательно: убрать «24 активных лота» / «420 000 ₽» / «18 ставок» / «4 этапа модерации» (D-09, D-08) — иначе демонстрация вводит в заблуждение; наполнить витрину 3–5 реальными featured-артистами с товарами (иначе блок артистов пуст, D-16); починить sticky-шапку и кнопку «Поиск» (D-17, D-18). Показывать корзину, заказ, оплату, ставку, торги, услугу, страницу персоны и карточку товара — **нельзя: их нет**.

### Можно ли начать закрытое тестирование?
**Пока нет.** Для закрытого тестирования нужны минимум: подтверждённый доступ к БД и наполненная витрина (Этап 0), честная витрина без фиктивных торговых данных (Этап 1), рабочий CI вместо сломанного `npm run lint` (D-15), и — обязательно — закрытие публичного репозитория `oukcion` плюс ограничение перебора кода кабинета (D-11, D-12). Тестировать можно только кабинет оператора; сценарии покупателя, услуги и аукциона не тестируются в принципе — соответствующего функционала нет.

### Можно ли принимать реальные заказы и проводить торги?
**Нет.** Отсутствуют: корзина и оформление заказа, платёжный провайдер (0 совпадений по stripe/ЮKassa/Тинькофф), расчёт суммы, комиссии и доставки, идентификация покупателя, подтверждение оплаты и возвраты, уведомления, избранное. Аукцион не существует: ни `auctions`, ни `lots`, ни `bids`, ни серверной фиксации ставки, ни победителя, ни обязательства по оплате. Реализовать и протестировать это — этапы 3 и 5.

### Пять первых действий с наибольшим результатом
1. **Закрыть `Shvachkomax/oukcion` (публичный) и зафиксировать один канонический репозиторий**, перенеся в него 20 коммитов. Пока правится устаревшая копия, любые правки не попадут в прод — это блокирует всю работу. (D-10, D-11)
2. **Восстановить доступ к Supabase-проекту Oukcion и наполнить витрину** 3–5 featured-артистами с опубликованными товарами: главная перестанет быть пустой, а расхождение «пусто / сломано подключение» будет закрыто. (D-16, D-09)
3. **Убрать фиктивные торговые данные с главной** («24 активных лота», «420 000 ₽», «18 ставок», «До конца 02:14:33», «4 этапа модерации») и починить `npm run lint`/`tsc`, добавить CI. Снимает главный риск «вводить в заблуждение» и даёт рабочий quality gate. (D-09, D-15, D-34)
4. **Поднять Next.js до ≥ 16.4.2 и закрыть риски доступа к кабинету** — critical RCE в текущей версии прод-бандла, публичный репозиторий и неограниченный перебор `CABINET_ACCESS_CODE` в одном репозитории. (D-14, D-11, D-12)
5. **Спроектировать и согласовать модель заказа (этапы 2–3): `catalog → карточка товара → корзина → заказ → оплата`** — это самый длинный путь и он определяет схему `products/orders/roles/RLS`, от которой зависят услуги и аукцион. Параллельно закрыть по мелочи интерфейсные дефекты (sticky-шапка, инертный «Поиск», кликабельность карточек, шрифты, alt-тексты). (D-02, D-05, D-06, D-17, D-18, D-19, D-21, D-22)
